# 5. Account Key Sets

## 5.1 Overview

Every account has a **key set**: a small bundle of random keys generated on the user's first device. Everything else in the vault is protected, directly or indirectly, by these keys.

| Key | Size | Purpose |
| --- | --- | --- |
| Account key | 32 bytes | Encrypts the user's personal data, such as settings and their own vault keys |
| X-Wing secret key | 32-byte seed | Receives shared vault keys from other users (Section 7) |
| Ed25519 secret key | 32-byte seed | Identity signatures, classical half |
| ML-DSA-65 secret key | 32-byte seed | Identity signatures, post-quantum half |

Each asymmetric key is stored as the 32-byte seed from which its standard key generation is run, so the whole secret part of a key set is exactly 128 bytes.

The key set never leaves the user's devices unencrypted. The server stores it only in *wrapped* form (5.4), next to the matching public keys (5.5).

The key set is independent of the master password. Changing the password, the Secret Key or the email address re-wraps the same key set; it does not change any key, so nothing shared with the user has to be re-encrypted.

## 5.2 Identifiers and versions

- **Account ID:** 16 random bytes generated by the client at account creation. It never changes, even if the email address does.
- **Key set version:** a 32-bit counter starting at 1. It increases only when the key set itself is replaced (5.6).

## 5.3 Key generation

```
account_key   = random(32)
xwing_seed    = random(32)
ed25519_seed  = random(32)
mldsa_seed    = random(32)
```

Public keys are derived from the seeds:

- **X-Wing** public key, as in draft-connolly-cfrg-xwing-kem, Section 5.2:
  ```
  expanded     = SHAKE256(xwing_seed, 96 bytes)
  (pk_M, sk_M) = ML-KEM-768.KeyGen_internal(d = expanded[0:32], z = expanded[32:64])
  sk_X         = expanded[64:96]
  pk_X         = X25519(sk_X, 9)
  xwing_pk     = pk_M ‖ pk_X                          (1216 bytes)
  ```
- **Ed25519** public key from `ed25519_seed`, as in RFC 8032 Section 5.1.5 (32 bytes).
- **ML-DSA-65** public key from `mldsa_seed` as the seed ξ of `ML-DSA.KeyGen_internal`, FIPS 204 Algorithm 6 (1952 bytes).

## 5.4 Wrapping

A wrapped key set is the key set encrypted under a 32-byte **wrapping key**. Protocol version 1 defines these wrapping methods:

| Method | Code | Wrapping key | Defined in |
| --- | --- | --- | --- |
| Master password | 1 | Account Unlock Key (`AUK`) | Section 3.5 |
| Passkey | 2 | Derived from the WebAuthn PRF output | Section 10 |
| Device | 3 | Device key held in the secure element | Section 10 |
| Recovery | 4 | Recovery key | Section 11 |

Encoding:

```
plaintext  = account_key ‖ xwing_seed ‖ ed25519_seed ‖ mldsa_seed        (128 bytes)

aad        = "BlackBoxus v1 key-set" ‖ u16be(1) ‖ account_id
             ‖ u32be(key_set_version) ‖ u8(method)

nonce      = random(24)
ciphertext = XChaCha20-Poly1305(wrapping_key, nonce, plaintext, aad)    (144 bytes)

wrapped    = u16be(1) ‖ u32be(key_set_version) ‖ u8(method) ‖ nonce ‖ ciphertext
                                                                         (175 bytes)
```

To unwrap, the client takes `account_id` from its own records, never from the wrapped value, rebuilds `aad`, and decrypts. It MUST reject the result if:

- the length is not exactly 175 bytes;
- the protocol version is not 1;
- the method is not the one the client is unlocking with;
- the key set version is lower than the highest version the client has previously seen for this account;
- decryption fails.

Because the account ID, key set version and method are bound into the associated data, a malicious server cannot swap one user's wrapped key set for another's, replay an old key set, or present a key set wrapped for one method as another.

## 5.5 Public key bundle

The public half of a key set is published as a signed bundle:

```
bundle     = u16be(1) ‖ account_id ‖ u32be(key_set_version)
             ‖ xwing_pk ‖ ed25519_pk ‖ mldsa_pk                          (3222 bytes)

signed     = bundle ‖ HybridSign(identity, "BlackBoxus v1 public-key-bundle", bundle)
                                                                         (6595 bytes)
```

The self-signature proves that whoever published the bundle holds its secret keys. It does **not** prove the bundle belongs to a particular person: a malicious server could publish a bundle of its own. That is the job of key transparency and out-of-band verification (Section 9).

### Hybrid signatures

```
HybridSign(identity, context, message) =
    Ed25519.Sign(ed25519_seed, lp(context) ‖ message)          (64 bytes)
  ‖ ML-DSA-65.Sign(mldsa_seed, message, ctx = context)         (3309 bytes)
```

- ML-DSA-65 signing uses the hedged variant with `random(32)` as `rnd` (FIPS 204, Section 3.4).
- `context` MUST be at most 255 bytes.
- A hybrid signature is valid only if **both** signatures verify. Ed25519 verification MUST use the strict rules of RFC 8032 Section 5.1.7 (`verify_strict`), rejecting non-canonical encodings and small-order keys.

## 5.6 Changing passwords and replacing key sets

| Event | What changes |
| --- | --- |
| Master password, Secret Key or email change | New `AUK` and `OPW` (Section 3), new OPAQUE registration (Section 4), key set re-wrapped with method 1. Key set version unchanged. |
| New passkey or device | A new wrapped copy for that method. |
| Suspected key compromise | A new key set with the next version, re-wrapped for every method, new public bundle; vault keys re-shared to it (Section 7). |

## 5.7 Security considerations

- **Server swap or rollback.** Bound associated data stops a malicious server from substituting or replaying wrapped key sets (5.4).
- **Quantum adversaries.** X-Wing and ML-DSA-65 keep shared keys confidential and identity signatures unforgeable even if X25519 and Ed25519 are broken. A captured wrapped key set is protected by 256-bit symmetric encryption.
- **Memory.** Seeds are erased after use. Expanded ML-KEM and ML-DSA secret keys are re-derived when needed and erased immediately afterwards.
- **Implementations.** ML-KEM and ML-DSA come from libcrux, whose implementations are formally verified. They are cross-checked in tests against the independent RustCrypto implementations.

## 5.8 Test vectors

[`vectors/05-key-sets.json`](vectors/05-key-sets.json) gives public keys derived from fixed seeds, a wrapped key set made with a fixed nonce, and a sample signed bundle. Signatures are randomised, so the sample is checked by verification rather than by fixed bytes.

The vectors are checked independently with OpenSSL (ML-KEM-768, ML-DSA-65, X25519, Ed25519) and libsodium (XChaCha20-Poly1305) by [`tools/vectors/verify_key_sets.py`](../../tools/vectors/verify_key_sets.py).
